Retry policy for the payments gateway client

Make transient gateway failures invisible to callers by retrying idempotent requests with jittered backoff, while guaranteeing a charge is never submitted twice.

Scope 5 files · 2 new Risk medium — touches the charge path Blocked on R3

Problem

GatewayClient treats every non-2xx response as terminal. The upstream provider returns 503 during its nightly failover window — typically three to five seconds, once or twice a night.

It surfaces as customers seeing “Payment failed, please try again” on a card that is perfectly good, and as a support ticket the next morning. Last month that was 214 checkouts across 9 incidents, every one of which would have succeeded on a second attempt 400ms later. Ops currently has no lever: the only workaround is a manual replay from the dead-letter queue, which is why the failures are found by customers rather than by us.

Approach

Put retry logic in a separate policy object that wraps the transport, not inside GatewayClient and not inside the HTTP adapter.

RetryPolicy owns one decision — given this outcome and this attempt number, retry after how long? — and knows nothing about payments, HTTP, or sleeping. GatewayClient keeps owning request construction and response parsing. Idempotency is enforced by minting an Idempotency-Key once per logical operation and reusing it across every attempt, so a retry after an ambiguous timeout is settled by the provider, not by us guessing.

Rejected: retrying inside the HTTP adapter (it cannot tell an idempotent charge from a non-idempotent refund), and a generic middleware stack (one call site, no second consumer — the abstraction would be speculative).

Components

RetryPolicy new

Pure function object. Takes an attempt number and a classified outcome (:retryable, :fatal, :timeout) and returns either a delay in milliseconds or :stop. Exponential base 2 from 100ms, capped at 2s, with full jitter, capped at 4 attempts.

Must not know about HTTP status codes, payments, the clock, or sleeping. It never performs the wait — it only says how long one should be. That is what makes it testable without a timer.

GatewayClient edit

Gains the attempt loop: classify the response, ask the policy, sleep, re-send the same request object with the same idempotency key. Emits one retry.attempt counter per retry and re-raises the last error when the policy says stop.

Must not know the backoff curve, the attempt ceiling, or the jitter strategy — those are constructor-injected as a policy. A test substitutes a zero-delay policy.

IdempotencyKey new

Mints a UUIDv4 per logical operation and memoises it in Redis under the operation's natural key (order_id) for 24h, so a retry from a different process after a crash reuses the key rather than double-charging.

Must not know whether a retry is happening. It answers "what is the key for this order", nothing else.

HttpTransport untouched

Stays a dumb send/receive. Explicitly out of scope: no retry, no backoff, no knowledge that a request may be repeated.

Sequence

  1. Mint the key once

    IdempotencyKey.for(order) is called before the attempt loop. Every attempt in this call reuses it.

  2. Send and classify

    The transport's result maps to one of three outcomes. A 409 Conflict from the provider means the key already settled — treated as success, not an error, and this is the case that makes retries safe.

  3. Ask the policy

    policy.next_delay(attempt:, outcome:) returns milliseconds or :stop. The client does not compute anything.

  4. Sleep, count, repeat

    Increment retry.attempt with the outcome as a tag, sleep, loop. On :stop, re-raise the last error so the caller's rescue clauses behave exactly as they do today.

Risks & open questions

  1. Retry amplification during a real outage. If the provider is down rather than failing over, four attempts per checkout quadruples load on a service already struggling.

    Mitigation: the 4-attempt ceiling plus full jitter bounds it at 4× with the peak spread over ~3.9s. A circuit breaker is the correct next step but is deliberately out of scope — it is a separate behaviour with its own state machine.

  2. Redis unavailable when minting the key. No key means no safe retry.

    Mitigation: fall back to a process-local UUID and set max_attempts: 1 for that call — degrade to today's behaviour rather than risk a double charge.

  3. Is a timeout retryable? A read timeout is ambiguous: the charge may have been applied. The idempotency key makes a retry safe, but only if the provider honours the key on a request it never finished processing.

    Decision needed: confirm from the provider's docs that keys are registered on receipt, not on completion. If they are not, drop :timeout from RETRYABLE and retry only explicit 503/429. This blocks Increment 3.

  4. Latency budget. Worst case adds ~3.9s to a checkout request that was previously failing fast.

    Mitigation: the checkout endpoint's timeout is 30s and p99 is 1.2s, so the headroom exists. Confirmed against the current SLO before the ceiling was set at 4.
