# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## ⛔ Never open `claude/vendor/mermaid.min.BOTS-DO-NOT-READ.js`

Do not `Read`, `cat`, `head`, `tail`, `grep`, `sed` or glob it, and never run a recursive search across `claude/` without `--exclude-dir=vendor`. It is a 3.4MB minified third-party bundle — roughly **750,000 tokens**, several times a context window — and reading it teaches nothing, because it is build output, not source. It is never hand-edited; a version bump is a re-download, documented under "Vendored bundles" in `README.md`.

Reference it **by path only**. Anything that needs it needs a *directory* — `$HOME/.claude/vendor` — never a handle on the file. This warning lives here because `CLAUDE.md` is the one file loaded into every session unprompted.

## What this is

Personal dotfiles for macOS. No build step, no runtime dependencies — config data consumed by external apps (zsh, git, ghostty, Claude Code, Magnet, OBS). The only executables are `setup.sh` and three scripts under `claude/`: `scripts/statusline.sh`, `hooks/block-inefficient-bash.sh`, `hooks/plan-artifacts-on-exit.sh`. This repo never runs those three — Claude Code invokes them, and they are tracked only to be symlinked into `~/.claude`. The pre-commit shellcheck/shfmt gate still covers them, globbing `*.sh` rather than scoping to `setup.sh`.

## Commands

```bash
./setup.sh                # idempotent; safe to re-run. Prompts (via `select`) for an OBS resolution.
bats test/                # the test suite — pins link()'s contract, setup_starship's branches, and the tracked starship.toml/zshrc
shellcheck setup.sh       # lint
shfmt -d -i 2 -ci setup.sh # format check; -d fails on a diff instead of rewriting
lefthook install          # once per clone — installs the pre-commit hook that runs all three
```

`lefthook.yml` scopes shellcheck and shfmt to `*.sh`, but **not** `bats test/` — the suite runs on every commit, including config-only ones.

### Testing gotchas

- `setup.sh`'s own `run()` step-wrapper **shadows bats' built-in `run` helper**. Sourcing `setup.sh` in a test makes every later `run` fail with `Permission denied`. `test/setup.bats` aliases bats' version *before* sourcing: `eval "bats_run() $(declare -f run | tail -n +2)"`. New tests must call `bats_run`, never `run`.
- `[[ "${BASH_SOURCE[0]}" == "$0" ]]` (`setup.sh:200`) guards the bottom execution block, so a test can source the file for `link()` and the `setup_*` functions without running the machine setup. Keep new top-level side effects inside that guard.

## Core architecture: three install strategies

The central decision is **how each app's config gets onto the machine**, chosen from how that app writes its own files. Read `setup.sh:31-58` (`link`) and the per-app comments first.

1. **File symlink** (zsh, git, ghostty) — `repo file → ~/dotfile`. Bidirectional: editing the live config, or `git config --global ...`, writes *through the symlink into the repo*, showing up as uncommitted diffs here.
2. **Directory symlink** (OBS) — `obs/<resolution>/ → ~/Library/Application Support/obs-studio`. OBS saves via temp-then-rename, which **replaces a file symlink with a real file** but leaves a *directory* symlink intact. Never downgrade OBS to per-file symlinks.
3. **Copy/import** (Magnet) — sandboxed Mac App Store app whose plist `cfprefsd` rewrites atomically, clobbering symlinks. Uses `defaults import`, and needs a manual `defaults export` to back changes up into the repo.
4. **Untracked runtime state** (the statusline colour DB) — a file a *tracked script* creates, deliberately neither tracked nor linked. `~/.claude/statusline-colors.db` holds per-session colour assignments; it is machine-local by definition (a colour belongs to this laptop's set of checkouts) and meaningless elsewhere. `setup.sh` does not create it — `claude/lib/session-colors.sh` does, on first use, with `CREATE TABLE IF NOT EXISTS`. For any future one of these, its *absence must be a working state*, not an error: the statusline falls back to hashing when the DB cannot be opened.

**Claude Code is strategy 1, but its destination directory is shared.** Every tracked file under `claude/` is a plain `link()`. Unlike zsh or ghostty, `~/.claude` is not a config directory — it is mostly Claude Code's runtime state (session transcripts, caches, plugin installs, shell snapshots, `history.jsonl`), machine-local and in places private. So links are **per-file, never a link of `~/.claude` itself**.

The same problem recurs one level down, hence two steps:

- `setup_claude` links the seven flat files (`global-instructions.md`, `settings.json`, `statusline.conf`, `context-window.conf`, `scripts/statusline.sh`, `lib/session-colors.sh`, `hooks/block-inefficient-bash.sh`). **`claude/global-instructions.md` is linked to `~/.claude/CLAUDE.md`** — the repo's only renamed link. Claude Code requires that filename; a `claude/CLAUDE.md` here would be read as *this* repo's project instructions, the job of the file you are reading. A test pins the rename, so restoring the old name fails the suite.
- `setup_claude_skills` links **one symlink per skill directory**, from a hardcoded list — not `claude/skills → ~/.claude/skills`, because Claude Code's *plugins* write into that directory. `skills/.ruby-lsp/` (a Gemfile and lockfile) is the ruby-lsp plugin's doing, and a directory symlink would aim that state at the repo. Per-skill links keep untracked things — plugin state, an uncommitted local skill — as real directories beside the symlinks, invisible to git. Adding a tracked skill therefore means adding its name to the loop; that explicit opt-in is the point. `test/setup.bats` pins this by reproducing the `.ruby-lsp` write and asserting it stays out of the repo, so a directory symlink fails the suite.

- `setup_claude_vendor` links **the whole `claude/vendor` directory** to `~/.claude/vendor` — the one directory symlink under `~/.claude`. The rule is not "never link a directory under `~/.claude`", it is *never link a directory something else writes to*. `~/.claude` and `~/.claude/skills` are shared with Claude Code and its plugins; nothing but this repo has ever written to `~/.claude/vendor`, so one link covers it. The payoff: a second vendored bundle needs no line in `setup.sh` — the opposite trade to skills, where the explicit list *is* the point. It is its own `run()` step, so a machine that fails it still gets `settings.json` and the hooks; a plan just renders without its diagram.

Unlike the other apps, `setup_claude_skills` records failures across its loop (`status=1`) instead of returning early, so one renamed skill does not skip the rest — the same record-and-continue shape as `run()` one level up.

**Starship spans two of these, on purpose** — a compiled Rust binary plus a config file are separate problems:

- The **binary** fits none of the strategies: nothing tracked to symlink, and cloning `starship.rs` gets only source, needing a Rust toolchain and a slow, fallible per-machine `cargo build`. So `setup_starship` shells out to `brew install starship` (strategy: *package manager*), behind an early `command -v starship` return so re-runs don't re-invoke brew, and a `command -v brew` guard returning non-zero with `skip:` rather than failing obscurely.
- The **config** (`starship/starship.toml`) is an ordinary tracked file: plain strategy 1, `setup_starship_config` `link()`s it to `~/.config/starship.toml`. It is a **separate `run()` step** so the config still lands where the brew install was skipped or failed, inert until the binary shows up.

There is no clone-and-pull strategy any more. It existed only for Spaceship (removed), and with it went `zsh_custom_dir()`, which parsed `ZSH_CUSTOM` out of `zsh/zshrc` to find oh-my-zsh's custom themes dir. Starship isn't an oh-my-zsh theme and never goes near that directory, so nothing reads `ZSH_CUSTOM` here now.

`run()` wraps each app's step and records failures instead of aborting (`set -uo pipefail`, deliberately **not** `-e`), so one broken step never blocks the rest.

## Consequences for editing

- Edits to `zsh/zshrc`, `starship/starship.toml`, `git/gitconfig`, `ghostty/config`, `claude/**`, and `obs/<res>/*` are *already live* where `setup.sh` has run — no reinstall step. They still need committing.
- **A new skill under `claude/skills/` is not installed until its name is added to the loop in `setup_claude_skills`.** Nothing globs that directory, deliberately (see above). A test asserts every name in that list has a `SKILL.md`, so a rename fails a test instead of silently dropping a skill.
- **The statusline's colour comes from a database, not a hash.** `claude/lib/session-colors.sh` records a colour per directory+branch in `~/.claude/statusline-colors.db` and **never reassigns an existing row**. That permanence is the feature: repainting a live session mid-work is a bug. Three details are load-bearing, each with a mutation-checked regression test:
  - `PRAGMA busy_timeout=10000` — without it a locked write is abandoned *silently* (11 of 24 parallel rows lost, zero stderr) or prints `database is locked`, discarding the whole statusline. The test asserts on **rows written**; a stderr-only assertion passes vacuously. The ceiling is a backstop against a machine stall, not a contention budget — real waits are sub-millisecond.
  - `INSERT OR IGNORE` — `OR REPLACE` lets the loser of a race overwrite the winner and repaint a live session.
  - The `SESSION_COLOR_PALETTE` **order** — assignment walks it, so adjacent entries go to sessions likely to be open together. Tuned for maximum adjacent CIELab distance (min ΔE 91.3); regenerate it, never hand-edit.

  **The palette is defined in exactly one place** — `SESSION_COLOR_PALETTE` in `claude/lib/session-colors.sh`. `statusline.sh` sources the library before it needs a colour, so the hash fallback indexes that same array. It keeps a tiny guarded default for when the library is unreadable, deliberately *not* a copy of the real list: a stale duplicate that silently disagreed is worse than an obviously reduced one. Changing the palette — contents **or length** — is a one-line edit in that file; the tests derive expectations from the array rather than restating it. Two tests pin this: one fails if a second `PALETTE=(...)` reappears in `statusline.sh` or the indexed read is renamed away, the other checks every code in the guarded default still clears the contrast bar.

  **Scoring the palette requires the terminal theme's real foregrounds**, not xterm's defaults — `#d9bd26` / `#1cd915` under ghostty `deep`. Getting this wrong shipped 7 of 16 codes below the 3.0 bar, because the swatch page used to pick them rendered colours the terminal never draws. Codes `0`–`15` are theme-resolved too, so they are **not** on the 6×6×6 cube and must not be mapped through it.

  Retention and the DB path are tunables in `claude/statusline.conf`, live via the symlink.
- **The context gauge is scaled to the auto-compact point, not the raw window.** Claude Code compacts once input tokens reach `CTX_MAX - CTX_RESERVE` (167,000 of 200,000). The reserve is an *absolute* output budget, not a fraction of the window: the 1M-window case compacts at ~967K, the same ~33,000 held back. Dividing by `CTX_MAX` made the bar read ~84% when compaction fired. `CTX_RESERVE=33000` is **empirical, not documented by Anthropic**: across 93 `compact_boundary` records, `200000 - preTokens` fell in a 32,852–33,273 band. The conf file carries the `jq` one-liner to re-measure it if compaction drifts.

  Both constants live in `claude/context-window.conf`, **not** `statusline.conf`, which holds only that script's *display* tunables. These describe when *Claude Code itself* compacts; the statusline merely consumes them, and any other hook or script needing the threshold should read the same file. `statusline.sh` sources it directly — not via `session-colors.sh`, which is sourced far later and skipped when unreadable — and defaults both values inline, so an absent or half-written conf still renders. Adding it to the flat-file list in `setup_claude` installs it.

  Token count and window size come from the payload's `context_window` object (`total_input_tokens`, `context_window_size`); the transcript sum is the fallback for older CLIs and the null window at session start. `context_window.used_percentage` is deliberately **not** used — it divides by the raw window and reads ~83.5% at compaction, which is the bug. `context_window_size` is clamped *down* to `CTX_MAX`, since `autoCompactWindow` can cap the effective window below the model's native one.
- **`claude/settings.json` names `scripts/statusline.sh`, `hooks/block-inefficient-bash.sh` and `hooks/plan-artifacts-on-exit.sh` by their `~/.claude/...` paths.** Renaming or moving either script without editing `settings.json` leaves Claude Code invoking a dead path silently — no warning. `test/setup.bats` pins the pairing.
- **Whether Claude Code's own writes to `settings.json` survive the symlink is unverified.** It rewrites the file when a setting changes inside a session: an in-place write follows the link into the repo, a temp-then-rename would replace the link with a real file (the OBS failure mode). The CLI's `config` subcommand is gone, so nothing non-interactive can trigger that write path and settle it. `README.md` documents the `ls -l ~/.claude/settings.json` check and the copy-back recovery. Claude Code also drops a timestamped `settings.json.<date>.bak` before rewriting, so nothing is lost either way.
- **A hook wires plan mode to `plan-writing`; nobody has to remember to invoke it.** `claude/hooks/plan-artifacts-on-exit.sh` is a `PreToolUse` gate on **`ExitPlanMode`**: it blocks the first exit (exit 2, stderr fed back to the model) telling it to run the skill, then allows the retry. **`PreToolUse` is load-bearing**, not incidental: the artifacts exist to be *reviewed and iterated on*, so they must reach the browser before the approval prompt, while the plan is still editable. `PostToolUse` would render the plan just as it stopped being reviewable. A test greps the block message for the browser-review wording, because a message that merely demands two files gets satisfied as paperwork on the way out. Three branches keep it from wedging plan mode, each with a regression test: it allows the exit once `PLAN.html` *and* `TODO.md` exist (otherwise it re-blocks its own retry and plan mode is inescapable), exits 0 for a non-git `cwd` (a scratch directory has no branch or PR to hang tasks off), and fails open on malformed input. `cwd` comes from the hook payload; `$PWD` is the hook's own directory.
- **Planning and doing are two skills, on purpose: `plan-writing` and `development`.** They were briefly one (`plan-artifacts`) and it was wrong: one file meant the planner carried the full execution contract it must not act on, and the *description* had to advertise both jobs, so neither triggered cleanly. The seam is the approval gate — `plan-writing` emits `PLAN.html` + `TODO.md` and **halts**; `development` does the work.
- **`development` was called `plan-execution`; the rename is the point, not cosmetics.** A skill described as *"execute an approved plan"* never fires, because **nobody labels the phase** — after approval you just start working, the same failure mode that forced `plan-writing` onto a hook. Naming it for the *activity* makes it trigger on "let's build X", with no plan in sight. So **the five steps apply to every piece of work, always**. The proportionality note ("a genuine one-line fix does not need PR ceremony") is deliberately two sentences; any more turns it into an escape hatch.
- **`development` owns the contract; `TODO.md` no longer does.** Step definitions, the `--no-verify` prohibition, TDD-inside-a-task, strict sequencing and halt semantics all live in the skill. They used to live in `TODO_TEMPLATE.md`'s header comment, copying ~19 lines of contract prose into every generated file — the user's rule is that a to-do list is *exactly* a to-do list, no other noise. The template now holds tasks, branches, checkboxes, steps and nothing else.
- **`plan-writing` is the instructions for writing a plan, not a renderer run after one exists.** It used to open with "plan the work as you normally would; this skill is about *what the plan is written to*". That post-hoc framing was the bug: it put the plan's *shape* nowhere editable, so changing how plans are made meant rewriting skill prose. Now **`assets/UI_TEMPLATE.html` is an input consulted while planning** — its sections are what the plan must cover, so reading it early changes what gets researched. `SKILL.md` therefore **must not restate the section list**: the template is the single definition, so retuning every future plan is an edit to one file. A test fails if the section names reappear in `SKILL.md`, another if the old wording returns.
- **The chat output is one line.** `ExitPlanMode`'s plan string is "I've generated the plan, available at `PLAN.html`" and nothing else — no summary, no headings, no bullets. The plan is read in the browser; pasting it into the terminal too is the duplication the artifacts exist to remove. Stated in three tested places: `SKILL.md`, the hook's block message, and the template. The hook's message was rewritten too — it used to say the skill "formats and splits" the plan and "does not replace your thinking", the same post-hoc framing hard-coded into the wiring; it now sends the model back to the template.
- **`plan-writing` bundles its own templates under `assets/`.** The prompt originally read `~/.config/claude-templates/{UI_TEMPLATE.html,TODO_TEMPLATE.md}`, which exists on no machine here. Tracking the templates inside the skill keeps it self-contained, and the per-skill directory symlink carries them along. `assets/` is what Claude Code's skill layout reserves for templates and fonts; its siblings are `scripts/` for executables and `references/` for docs loaded on demand — why `clean-code` keeps its chapters under `references/`. The `~/.config` path stays a documented *override*, not a dependency: the skill must still work without it.
- **`PLAN.html`'s Mermaid must be a classic `<script src>` off the vendored bundle — an ESM `import` does not work.** `PLAN.html` opens from `file://`, where a module import fails with *"Failed to fetch dynamically imported module"* **even for a local file**: module fetches obey CORS, and `file://` origins are opaque. A plain `<script src>` is exempt and loads the same local file fine. Verified in headless Chrome both ways — the ESM form rendered no `<svg>`, the classic form renders one with `aria-roledescription="sequence"`. The CDN URL it arrived with (`cdn.jsdelivr.net`) is doubly wrong: unreachable offline, pointless once vendored. A test greps the template for the vendored `<script src>` and asserts `cdn.jsdelivr.net` and `type="module"` are both absent, because "modernising" it back breaks every diagram *silently* — no console error, no failed load, the diagram source just sits there as text.

  **The bundle lives in `claude/vendor/`, deliberately not in the skill's `assets/`.** `assets/` is documented as "templates the skill reads", and pointing an agent at a 750,000-token file it is told to read is the accident to avoid. `DO-NOT-READ` in the filename is load-bearing for the same reason: the warning travels in every path that mentions it.

  **The template substitutes `{{VENDOR_DIR}}` — the directory, not the file path.** It must be absolute and expanded: `PLAN.html` is written into whatever repo is being planned in, so relative cannot resolve, and HTML does not expand `~`. Hardcoding `/Users/jm/...` into a *template* was tried and rejected — it bakes in a username and works on one machine; a test now fails on any `/Users/` in the template. The **directory** rather than the file path is also deliberate: a whole-file placeholder invites the generating model to stat, verify or open what it names; a directory placeholder is resolved and dropped. The filename stays literal template text. The `AGENT / LLM` comment must sit **immediately above** the `<script>` line with nothing between, and is copied into every generated `PLAN.html` — a file agents open later. A test asserts the adjacency, not merely that both strings exist, because adjacency is what rots silently.
- **The five-step contract is the user's spec, not a default — and the unit is a *task*.** It was called an "increment" until the user renamed it; the meaning is unchanged, the old name recorded only so the history parses. A task is *a slice of work worth its own pull request* — deliberately not "one behaviour, one failing test", which an earlier draft asserted and which is wrong here: TDD loops **inside** a task (test, code, test, code), the whole cycle landing in one commit. The steps carry the user's exact lowercase names, also their `TODO.md` labels: `writing tests` → `coding` (refactor and the relevant-tests-only run are *inside* this step, not separate) → `bot review` (`/code-review high`, with fixes) → `draft pr` → `author review`.

  Five, not the earlier six, because **commit-and-push merged into `draft pr`**: a GitHub draft PR cannot exist without a commit and push behind it, so a separate commit step was redundant. That merge is the risky edit — the commit step is where **`--no-verify` is never allowed** lived, and folding it in is how that rule gets lost. It is therefore restated under `draft pr`: a failing pre-commit hook is fixed within that step, which is not done until the push succeeds.

  Three more parts are stated explicitly. The test moves first for *changes* as well as additions — the habit breaks when modifying existing behaviour, where the reflex is to edit code and fix up the tests it breaks. `author review` is a hard stop, ending only when the PR is ready for review or the user says so. Tasks run strictly sequentially — no parallel branches. **Branch creation is implicit at the task's start, not a step** — the repo already exists and the plan names the branch.

  **Five is a baseline, not a fixed contract.** Claude may add a step a task genuinely needs (a migration, a manual verification) in the same lowercase style; an added step must appear in `PLAN.html` so the user can veto it before work starts. A `/statusline $(./parse_status.sh)` sync appeared in the source prompt and was dropped deliberately: no such script exists in any repo here.
- **`TODO.md`'s status is derived from the checkboxes, never declared.** No status column, no front-matter, no marker comments — a declared status can disagree with the boxes, a derived one cannot; the old Progress table was that duplication. The three states: *not started* (task unchecked, zero steps checked), *in progress* (task unchecked, ≥1 step checked), *completed* (task checked, all steps trusted done). The current step is the first unchecked one, and **every task lists all its steps whatever its state**, so a visualiser can show what is pending. The task's checkbox sits in its heading — `## - [ ] Task 3: …` — keeping task and state on one line.

  **Parseability here is a uniformity requirement, not a marker one.** A script must answer "which are done, which is in progress, what step, what's left" without encoding edge cases, so every task heading and step line is identical in form: steps always numbered, the short name always in the same position. Do not vary it for readability. The template carries the grep/awk a script would use, in the comment deleted on generation. Verified against a three-state example with an added `migration` step.
- `claude/skills/format-technical-response` does not exist on purpose: the `~/.claude/skills` directory was empty (no `SKILL.md`), so there was nothing to track.
- `zsh/agnoster.zsh-theme` is still tracked and installed by `setup_zsh` on purpose: it makes reverting the prompt a one-word `ZSH_THEME` change in `zsh/zshrc`. Don't delete it as dead config.
- **`zsh/zshrc` has `ZSH_THEME=""` deliberately.** Starship owns `$PROMPT`; a non-empty oh-my-zsh theme would race it. The `eval "$(starship init zsh)"` line must stay **below** `source $ZSH/oh-my-zsh.sh` — that line assigns `$PROMPT`, so an init above it is silently overwritten — and must keep its `command -v starship` guard so a machine without the binary still gets a working shell.
- **`starship --version` exits 0 on a broken config.** A TOML syntax error goes to *stderr* and starship carries on with its built-in defaults; same for `starship module`/`prompt`. So any check that a config parses must assert **stderr is empty**, never exit status — `test/setup.bats` does this, and a status-only check there passes vacuously (verified against 1.26.0).
- `git/gitconfig` is machine-tainted: absolute `/Users/<username>/` paths (`core.excludesfile`, `commit.template`) and a work email. Expect those to drift per machine.
- `obs/` is inverse-gitignored (`.gitignore:6-9`): everything under `obs/*/` is ignored except `global.ini`, `user.ini`, and `basic/`. That keeps OBS's logs, caches, plugin binaries, and the **obs-websocket password** out of commits. A new tracked OBS file requires a new `!` negation.
- `bash/`, `tmux/`, and `vim/` are tracked but **not wired into `setup.sh`** — legacy configs, installed by hand if at all.

## Adding a new app

1. Determine how the app writes its config (in-place edit / atomic rename / `cfprefsd`) — that picks the strategy.
2. Add a `setup_<app>` function returning non-zero on failure; register it with `run "<app>" setup_<app>`.
3. If the app writes non-portable junk into a directory you want to link, use one of the two ways this repo already handles that. **Link the directory and gitignore the junk** (OBS) when the app owns the whole directory and you want its edits to autosave. **Link individual files/subdirectories** (Claude Code) when the directory is *shared* with state that should never be in the repo at all. The first keeps junk on disk inside the repo but out of commits; the second keeps it out entirely, at the cost of an explicit list to maintain.
4. Document it in `README.md` — the user-facing doc, covering per-app rationale and manual backup commands.
